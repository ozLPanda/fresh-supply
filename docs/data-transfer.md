# Перенос данных сайта в десктоп

Данные сайта можно загрузить через API в пустую локальную базу, а затем обновлять
локальную копию командой объединения. Источник — backend этого проекта, цель — собственная
PostgreSQL-база приложения. После переноса сайт и десктоп работают независимо.

## Как загрузить данные

1. Установить приложение. При первом запуске создать локальный доступ; далее
   приложение предложит загрузку с сайта. В уже настроенной программе открыть
   «Файл → Загрузить данные с сайта…».
2. Указать базовый URL backend, например `http://localhost:8084`, телефон и пароль
   своей учётной записи на сайте. Для отдельного компьютера указать доступный адрес
   его backend; `localhost` всегда означает тот ПК, где запущен десктоп.
3. Нажать «Загрузить данные» и дождаться завершения. Приложение само авторизуется,
   скачивает архив, проверяет состав и переносит записи и файлы.
4. Войти в десктоп с телефоном и паролем сайта. Начальный локальный аккаунт заменён
   перенесёнными аккаунтами. Пароли пользователей остаются исходными; активные
   сеансы входа сайта в десктоп не копируются.

Источник должен иметь метод `GET /api/data-transfer/export` и пользователь должен
иметь право **«Экспорт всех данных и файлов»** (`data.export`). Миграция V134 выдаёт его
роли «Администратор». Доступ к отдельным страницам управления сам по себе не даёт
права полного экспорта. URL, телефон и пароль вводятся в приложении; не включать
пароль или ключ доступа в URL. Пароль и Bearer-токен используются только в памяти;
созданный для загрузки сеанс сайта отзывается после скачивания.

Если сайт работает на прежнем backend без нового метода, сначала обновить его
backend. Эта реализация добавлена в `ovoshi-help`; исходные справочные проекты
`firm-active-company-shop` и `hackalem-ai-base` не изменялись.

## Что переносится

Все прикладные таблицы текущей схемы: каталог, цены, поставщики, покупатели,
пользователи, роли и права, заказы и позиции, кошельки и операции, склад и документы,
история, настройки и остальные бизнес-записи. Сохраняются идентификаторы, точные
десятичные значения, JSON, бинарные поля, векторы и счётчики артикулов/документов.
Также переносятся изображения и документы из хранилища сайта в нативное файловое
хранилище десктопа; фотографии ассистента в JSON переносятся вместе с таблицами.

Не копируются действующие сеансы входа, подписки устройств Web Push, API-ключи
внешних клиентов и их технические журналы. Эти таблицы явно указаны в манифесте
архива. Flyway-история остаётся локальной; перенос не запускает SQL, полученный
с сайта. Настройки окружения, MinIO/DB-пароли и ключи GPT/WhatsApp из `.env` не
экспортируются. Подключения внешних сервисов настраиваются отдельно.

## Как обновить уже загруженные данные

1. Сохранить изменения в открытых формах. Открыть «Файл → Обновить данные с сайта…»
   и указать URL backend и учётную запись с правом `data.export`.
2. Нажать «Обновить данные». Приложение проверит снимок, создаст резервную копию
   текущей базы и файлов, затем объединит данные.
3. Проверить результат: число добавленных и обновлённых записей, сохранённых
   локальных версий и конфликтов. Отчёт и резервная копия остаются на компьютере.

Обмен выполняется только **сайт → десктоп**. Новые записи сайта добавляются;
локальные записи, отсутствующие на сайте, сохраняются. Для совпавшей записи
побеждает строго более позднее изменение. При одинаковом времени и разных данных
или неизвестном времени локальная версия сохраняется с записью о конфликте.
Время сравнивается с точностью PostgreSQL до микросекунд.

У каждой записи есть постоянный идентификатор. Совпавшие числовые ID независимо
созданных товаров или других объектов не считаются совпадением самих объектов:
приложение выделяет новый локальный ID и переносит ссылки. Позиции и другие
принадлежащие заказу/документу записи согласуются вместе с владельцем; неоднозначный
состав сохраняется целиком. Финансовые операции требуют согласованного журнала и
пересчёта баланса/складской себестоимости, а не копирования отдельной цифры баланса.
Файлы объединяются; разные файлы с одинаковым исходным ключом получают разные ключи.

Для объединения обе стороны должны поддерживать экспорт версии 2 и миграцию V135.
Первичная загрузка и отдельная полная замена совместимы с прежним экспортом версии 1.
У уже перенесённых старых данных нет полной истории изменений: UUID и проверяемое
время создания помогают сопоставить записи, но недоказуемые совпадения остаются
конфликтами. Время старых неизвестных изменений не заменяется датой обновления программы.

Для намеренной полной замены предусмотрено «Файл → Заменить все данные копией сайта…».
После проверки архива программа отдельно просит подтвердить «Заменить данные».
В этом режиме рабочая база и файлы становятся полной копией сайта; локальные
отличия остаются в резервной копии. Отсутствующие на сайте записи удаляются только
при полной замене, а не при обычном обновлении.

При отмене или ошибке скачивания текущая копия сохраняется. Ошибка после начала
применения запускает восстановление резервной копии. Адрес текущего приложения
нельзя использовать в качестве источника.

## Пустая база и сохранность данных

Пустота проверяется по всем прикладным таблицам и локальным файлам, а не только по
числу товаров. Эта проверка относится к первичной загрузке. В новой установке допустимы её системные роли, администратор,
нулевой кошелёк, склад MAIN и исходные настройки. Собственные пользователи,
изменённые права, настройки, баланс, документы или файлы блокируют импорт.

Для старой пустой установки 0.1.0 без сохранённого отпечатка сравнивается полный
набор системных записей с проверенным эталоном текущей сборки. Текущее состояние
произвольной базы никогда автоматически не объявляется пустым. После скачивания
проверка повторяется с остановленными backend и поиском, чтобы не пропустить
изменения, произошедшие во время загрузки.

Перед импортом создаётся согласованная резервная копия. Строки загружаются одной
транзакцией с проверкой всех внешних ключей; файлы заменяются после остановки БД.
Ошибка запуска возвращает первоначальную копию. Журнал вне каталога данных
позволяет восстановить её после аварийного завершения программы. Обычное закрытие
окна во время переноса временно блокируется.

Первичная загрузка не перезаписывает существующие данные. Повторное обновление
объединяет данные; полная замена остаётся отдельной явно подтверждаемой командой.
Постоянного фонового обмена и отправки данных на сайт нет.

## API и формат

`GET /api/data-transfer/export` принимает обычную cookie-сессию сайта или Bearer
авторизацию. Ответ `application/zip`, `Cache-Control: private, no-store`.
До выдачи ответа backend строит целый архив; отсутствие или изменение требуемого
файла отменяет экспорт. На время создания снимка новые HTTP-запросы изменения
данных ждут завершения экспорта; скачивание готового архива уже не удерживает блок.

Архив содержит `manifest.json` формата `ovoshi-help-data-transfer`, версии 1 или 2,
JSONL таблиц, файлы `.object`, схемы столбцов, счётчики и SHA256 каждого элемента.
Версия 2 запрашивается через `GET /api/data-transfer/export?format=2` и добавляет
проверяемый поток `sync/rows.jsonl`: экземпляр источника, UID, ключи, время изменения,
поколение записи и принадлежность агрегату. Служебные `sync_*` таблицы не копируются
как бизнес-данные; их идентичность и часы восстанавливаются отдельным локальным
доверенным кодом. Версия 1 остаётся форматом по умолчанию для старых клиентов.
Значения строк передаются текстом или null, чтобы сохранить bigint и decimal.
Импорт проверяет таблицы/столбцы по локальной схеме, полноту набора, размеры,
контрольные суммы, пути, форматы объектов и связи файлов с записями. Неподдерживаемые
схемы или более новая версия схемы требуют совместимого обновления приложения.

HTTP с учётными данными допускается для loopback и частных IPv4-адресов локальной
сети. Для публичного источника нужен HTTPS. Переадресации с авторизацией не
выполняются. Текущие пределы: архив до 4 ГиБ, распаковка до 10 ГиБ, строка JSONL
до 64 МиБ, до 10 млн строк одной таблицы. Превышение отменяет перенос до изменения
целевой базы; часть данных не импортируется молча.
Для объединения дополнительный предел метаданных — 250 тыс. записей вместе
с историей удалений и 128 МиБ потока sync. Превышение также оставляет базу целой.

## Проверки

Модульные тесты проверяют доступ, снимок, файлы, повреждённые архивы, заполненную
цель, откат и прерывание. Интеграционный скрипт
`desktop/scripts/smoke-data-transfer.cjs` создаёт два собственных временных native
runtime и проходит настоящий HTTP login/export/import. Проверяются суммы, складской
документ и FK, настройки, счётчики, изображение, вход и повторный запуск. Повторная
загрузка проверяет полную замену данных и файлов, отмену, недоступный источник,
откат при ошибке запуска и пригодность прежней резервной копии для восстановления. Реальные
базы и файлы пользователей этот тест не открывает.

`desktop/scripts/smoke-data-merge.cjs` проверяет одностороннее объединение двух
временных баз: локальные заказы, более свежие версии с обеих сторон, совпадения
числовых ID, перенос FK, номера заказов, сохранение начислений и отсутствие дублей.
Проведённые поступления на двух сторонах дают общий остаток и FIFO-слои;
отдельные финансовые операции дают общий баланс с сохранением журнала.
Ошибка финальной сверки после запуска проверяется с восстановлением прежней базы.
