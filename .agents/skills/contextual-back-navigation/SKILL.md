# Возврат туда, откуда пришёл пользователь

При создании или изменении формы, карточки или страницы с действием «Назад» сразу
закладывай контекст возврата. Одна и та же карточка может открываться из разных
разделов. Кнопка возвращает в фактическую точку входа; если её нет, использует
стандартную страницу для этого сценария.

## Реализация

1. Изучи текущий роутер и существующие соглашения навигации. Используй имеющийся
   механизм; не добавляй новый роутер или библиотеку ради этой функции.
2. Определи fallback для страницы: например, список товаров для карточки товара.
   Выбирай по структуре продукта; не отправляй все страницы на главную.
3. В точке перехода сохраняй адрес источника, включая pathname, query и значимый
   hash. Сохраняй фильтры, поиск, сортировку и пагинацию списка. Если они находятся
   вне URL, используй существующий механизм восстановления состояния списка;
   позицию прокрутки восстанавливай средствами приложения, когда это применимо.
4. Передавай контекст вместе с конкретным переходом — например, через state
   записи роутера. Не используй одну глобальную переменную «последняя страница»:
   независимые переходы и вкладки не должны перезаписывать друг другу источник.
   Контекст должен переживать обновление текущей страницы в той же вкладке.
   Если выбранный механизм этого не обеспечивает, используй поддерживаемое
   роутером или приложением сохранение, привязанное к текущей записи/переходу.
5. При нажатии «Назад» проверь источник и вернись в него. При отсутствии,
   повреждении или недопустимости контекста используй fallback.
   Прямая ссылка и новая вкладка без перенесённого контекста — нормальные случаи.

Сохраняй только нужные навигационные данные: не передавай в адресе возврата или
контексте пароли, токены, содержимое формы и полные объекты сущностей.

Адрес возврата считай недоверенным, особенно если он пришёл из query. Проверяй
разобранный URL и допустимость маршрута: разрешены только внутренние маршруты
приложения, доступные в данном сценарии. Исключай внешние адреса, `//host`,
опасные схемы и возврат на саму текущую страницу. Одна проверка `startsWith('/')`
недостаточна. Навигационный контекст не заменяет проверку доступа.

Не используй `history.back()` / `navigate(-1)` как единственное решение и не
считай `history.length > 1` доказательством корректного источника. Предыдущая
запись может вести на другой сайт или промежуточный экран. Возврат на один шаг
подходит, когда предыдущая запись подтверждённо является нужным источником;
иначе используй явный проверенный маршрут. Продумай push/replace, чтобы кнопка
«Назад» не создавала цикл «список → карточка → список → карточка».

Для вложенного сценария, например «список → карточка → редактирование», сохраняй
контекст каждого уровня: из формы — в карточку, из карточки — в исходный список.
При возврате сохраняй контекст самой карточки. Учитывай существующую защиту
несохранённых изменений. Не меняй автоматически поведение сохранения формы,
кнопки «Отмена» и системной кнопки браузера: это отдельные продуктовые действия.

## Проверка поведения

Проверь применимые сценарии вручную или существующими тестами навигации:

- Из списка товаров с поиском и пагинацией → карточка → «Назад»: тот же список
  с теми же параметрами.
- Из другого раздела, например заказа → та же карточка → «Назад»: исходный заказ.
- Прямая ссылка без контекста → «Назад»: стандартный список товаров.
- Обновление карточки после перехода из списка: источник сохранён.
- Независимые переходы в двух вкладках: источники не смешиваются.
- Некорректный или внешний адрес возврата: используется fallback.
- Вложенная форма и повторная навигация: нет потери исходного контекста и циклов.

В результате реализации кратко укажи выбранный fallback и проверенные сценарии.
