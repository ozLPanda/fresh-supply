# Поиск и переиспользование компонентов

## Сначала найти подходящее

1. Начни с `frontend/COMPONENTS.md`: найди компоненты по назначению и сценарию использования. Для UI используй также `.agents/skills/company-shop-ui/references/components.md` и правила `company-shop-ui`.
2. Прочитай исходники только подходящих кандидатов и при необходимости один пример использования. Проверь актуальные props, зависимости, состояния и ограничения. Каталог помогает сузить поиск, но код остаётся источником истины.
3. Если в каталоге нет подходящего компонента, выполни точечный поиск через `rg` по назначению, экспортам и местам использования. Отсутствие записи не означает отсутствие компонента. Не читай подряд все файлы проекта.
4. Переиспользуй ближайший подходящий компонент или расширь его совместимым API. Если совпадает лишь часть интерфейса, используй композицию или выдели общую часть. Создавай новый компонент только когда существующие не подходят; не превращай компонент в набор несвязанных режимов ради формального переиспользования.

## Где должен находиться компонент

- Компонент, используемый только внутри одного модуля, остаётся в этом модуле. Запись в каталоге сама по себе не делает его общим.
- Когда компонент из одного модуля начинает использоваться в другом, перенеси общую реализацию из исходного модуля в подходящую общую папку. Не оставляй межмодульные импорты внутренних UI-компонентов и не создавай копию вместо переноса.
- Универсальные визуальные компоненты размещай в `frontend/src/shared/ui`. Для общих предметных блоков используй существующую общую структуру проекта; если её нет, выдели тематическую папку в `frontend/src/shared/components/<область>`. Не смешивай бизнес-сценарии с базовыми UI-примитивами.
- Перед переносом проверь зависимости. Общий компонент не должен импортировать страницы, приватные хуки, API или состояние исходного модуля. Передавай необходимые данные и действия через типизированные props; при необходимости оставь получение данных и специфичную логику в локальной обёртке и вынеси только общую часть.
- Перенеси связанные стили и необходимые ресурсы, обнови все импорты и публичные экспорты. Проверь отсутствие циклических зависимостей и оставшихся ссылок на старый путь. Сохрани поведение существующих потребителей.

## Краткий каталог компонентов

Веди `frontend/COMPONENTS.md` на русском языке. Это индекс поиска: для каждого файла указывай название экспортируемого компонента или семейства компонентов, ссылку на файл и 1–2 предложения о назначении и подходящем случае использования.

- Разделяй общие UI-компоненты, общие предметные компоненты и локальные самостоятельные компоненты форм. Для локальных явно отмечай область использования.
- Для нескольких тесно связанных экспортов из одного файла достаточно одной записи. Соседний CSS отдельно не описывай. Не включай каждую страницу, внутреннюю функцию или список всех props.
- Не дублируй подробный API-справочник: при необходимости ссылайся на него или на существующий пример. Используй относительные ссылки, чтобы каталог работал в репозитории.
- При создании, переносе, изменении назначения или удалении компонента обновляй каталог в той же задаче. При переносе замени старую запись и путь, не оставляй дубли.
- Если каталог отсутствует или неполон, добавь проверенные записи для затронутых компонентов и подходящих найденных кандидатов. Не превращай обычную задачу в полный аудит всех компонентов и не описывай непроверенные возможности.

## Проверка результата

Проверь корректность ссылок и краткость описаний каталога. Для изменений кода выполни подходящие проверки типов и сборки по правилам проекта; после переноса проверь всех потребителей. Визуальные изменения проверь в реальном интерфейсе, включая отступы, адаптивность и взаимодействия согласно `company-shop-ui`. Для изменения только каталога или скилла сборка приложения не нужна.

В отчёте кратко укажи, что переиспользовано или почему понадобился новый компонент, что перенесено и обновлён ли каталог. Не заявляй о проверках, которые не выполнялись.
