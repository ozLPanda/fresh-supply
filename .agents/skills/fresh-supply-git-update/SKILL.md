# Fresh Supply: push и команды обновления

Результат запроса на push — опубликованные изменения и готовые команды для их
применения на ПК пользователя. Не заканчивай ответ только ссылкой на коммит и
не предлагай пользователю отдельно попросить инструкцию обновления.

## Команды обновления — только текст для пользователя

При запросе «пуш в гит» выполни согласованные Git-действия и проверки, а команды
обновления приложения **только напиши в финальном ответе в Markdown-блоке
кода `bash`** и кратко объясни. Пользователь выполняет этот блок самостоятельно.

Не запускай этот блок через терминал, SSH, Docker-инструменты или другие средства
ни на текущем Mac, ни на Windows/WSL, ни на другом сервере. Это относится и к
проверкам из инструкции: `docker compose ps`, просмотру логов и `curl`.
Доступ к компьютеру или просьба показать команды не означают разрешение их выполнить.
Выполнение обновления агентом допускается только по отдельному явному поручению
пользователя. Правила ниже определяют **содержание инструкции**, а не действия
для автоматического исполнения после push.

## Окружение

- Репозиторий: `https://github.com/ozLPanda/fresh-supply`; локальная папка на Mac
  может называться `ovoshi-help`. Проверяй fetch/push URL и ветку перед публикацией;
  учитывай HTTPS и SSH варианты того же репозитория. Последняя согласованная ветка — `main`.
- ПК пользователя: Windows, Ubuntu в WSL, Docker Desktop с WSL Integration.
  Известная папка клона: `/mnt/c/Users/User/fresh-supply`. Пользователь выполняет
  показанные команды в Ubuntu из корня клона. При уточнённом пути используй новый путь.
- По умолчанию это development Compose из `docker-compose.yml`, проект `ovoshi-help`.
  `frontend/` и `backend/` подключены через bind mounts. Публикация в Git сама
  по себе не обновляет ПК. Запрос на push не означает разрешение выполнять deploy
  или сброс данных на другом компьютере: здесь нужно дать пользователю команды.
- Если пользователь явно работает с production Compose, другим хостом или веткой,
  прочитай соответствующую конфигурацию и адаптируй команды; правила HMR и bind
  mounts нельзя автоматически переносить на production-образы.

## До и после push

1. Проверь status, staged diff, remote и исходящий диапазон коммитов.
   Включай только изменения текущей задачи; незавершённые работы других задач
   в этой общей папке не публикуй. Учитывай файлы всех отправляемых коммитов,
   а не только последнего. Сохрани сведения о диапазоне до push.
2. Прочитай раздел Container workflow в [AGENTS.md](../../../AGENTS.md) и актуальные
   Compose/Dockerfile затронутых сервисов. Эта таблица — основной источник выбора
   действий; не копируй её целиком в ответ и не назначай всем сервисам один restart.
3. После успешного push проверь удалённый SHA. Если push не прошёл, сообщи причину;
   не выдавай неопубликованные изменения за доступные через `git pull`.
4. В финальном ответе укажи репозиторий/ветку, коммит, результат проверок и сразу
   дай короткий блок команд для ПК. Для нескольких типов изменений объедини
   нужные действия без повторного перезапуска одного сервиса.

## Как выбрать команды

- Java, ресурсы backend, обычные Flyway-миграции и `pom.xml`: после pull нужен
  `docker compose restart backend`; простой `up -d` уже работающий процесс не обновит.
- Только UI/CSS/assets в bind mount: pull и обновление страницы; Vite применяет HMR.
  Конфиг Vite обычно перезагружается автоматически; restart frontend — если не применился.
- Зависимости frontend: применяй действие из AGENTS.md с установкой зависимостей
  в контейнере; не ограничивайся HMR. Проверь CMD актуального Dockerfile перед выбором.
- Runtime-настройки Compose: `docker compose up -d --no-build --no-deps СЕРВИС`.
  Изменение готового `image:`: сначала `docker compose pull СЕРВИС`, затем это
  пересоздание. Обычный restart не применяет новую конфигурацию контейнера.
- Изменения входов сборки образа (Dockerfile, COPY, системные пакеты, зависимости
  импортера; embedding-service без bind mount):
  `docker compose up -d --build --no-deps СЕРВИС` только для затронутого сервиса.
  Если для того же сервиса изменились и код, и образ/Compose, выбери более полное
  действие один раз: сборка с пересозданием вместо дополнительного restart.
- Документация, тесты и навыки без runtime-изменений: достаточно pull;
  прямо скажи, что контейнеры перезапускать не требуется.
- `--no-deps` используй для обновления сервиса в уже работающем стеке.
  Для остановленного стека с готовыми образами нужен `docker compose up -d --no-build`;
  для новой установки проверь наличие образов и отдельные инструкции первого запуска.
- Не предлагай `down`, `down -v`, удаление volumes, prune или полный rebuild
  как обычное обновление. Не добавляй reset/stash для обхода ошибки pull.
  При локальных изменениях или расхождении веток сначала разберись с ними.
- Для `B015__empty_project.sql` и аналогичных baseline-изменений поясни:
  они влияют только на новую базу. Pull/restart не очищает текущий каталог.
  Сброс данных — отдельный явно запрошенный сценарий, не часть push/update.

## Формат ответа пользователю

Дай один подходящий сценарий для известных условий, а не перечень всех вариантов.
Подставь реальные сервисы, ветку и путь; не оставляй «СЕРВИС» в готовых командах.
Используй `git pull --ff-only`; если требуется конкретная ветка, проверь её перед pull
и не предлагай незаметное переключение чужого рабочего дерева.
Зависимые действия связывай через `&&`, чтобы restart/build не выполнялся после ошибки pull.

Пример для уже работающего стека и изменения Java backend на `main`:

```bash
cd /mnt/c/Users/User/fresh-supply &&
git pull --ff-only &&
docker compose ps &&
docker compose restart backend &&
docker compose ps backend
```

Добавь проверку, соответствующую обновлённому сервису. Для backend:

```bash
docker compose logs -f --tail 60 backend
```

Объясни, что надо дождаться `Started ...Application`, после чего `Ctrl+C`
закроет только просмотр логов. Затем можно проверить
`curl -fsS --max-time 10 http://localhost:8084/actuator/health` и открыть
`http://localhost:5175/admin/login` (адаптируй порты по текущей конфигурации).
Статус контейнера `Up` ещё не означает готовность Spring: первый запуск скачивает
Maven-зависимости и применяет миграции. При `ECONNREFUSED` проверь завершение запуска.
Не сообщай, что приложение на ПК уже обновилось, пока пользователь или реальная
проверка на этом ПК этого не подтвердили. Если известный установленный коммит старее
текущего push, учитывай весь диапазон обновления и его зависимости.
