# fresh-supply для Windows и macOS

Настольная оболочка Electron использует общий React-интерфейс и запускает
локальные Java backend, PostgreSQL с pgvector и сервис поиска с multilingual E5.
Java, Python, база и модель включаются в установочный пакет. Пользователю не нужны
Docker, Node, Maven, отдельная Java или интернет для запуска локальных функций.

Поддерживаемые сборки: macOS 14+ на Apple Silicon и Windows x64. Windows нужно
проверять на Windows; запуск Mac-сборки не подтверждает совместимость Windows.
Intel Mac пока не входит в матрицу сборки.

## Установка и первый запуск

На Mac открыть `.dmg` и перенести `fresh-supply.app` в «Программы». На Windows
запустить `.exe`-установщик. При первом запуске указать свой телефон и пароль
администратора (минимум 16 символов). Вход выполняется по этому телефону.
Это новая пустая локальная база; данные сайта автоматически не копируются.
Для загрузки данных сайта предусмотрены предложение при первом запуске и
«Файл → Загрузить данные с сайта…». Укажите URL backend и учётную запись с правом
полного экспорта. Первичная загрузка разрешена только в пустую локальную базу.

Если после переноса продолжали работать на сайте, выберите
«Файл → Обновить данные с сайта…» и укажите тот же адрес backend и учётную запись.
Программа скачает и проверит свежую копию, затем попросит подтвердить полную замену
локальных данных и файлов. Изменения, сделанные только в приложении, будут заменены
данными сайта. До замены создаётся резервная копия; при ошибке программа восстанавливает
прежние данные. Отмена подтверждения сохраняет текущую базу без изменений.
Вернуться к предыдущим данным можно через «Файл → Восстановить из копии…».
Это перенос полной копии, а не объединение изменений сайта и приложения.
Подробнее: [перенос данных](../docs/data-transfer.md).

Приложение автоматически запускает компоненты и открывает `/admin/login`
только после проверки готовности базы и поиска. Компоненты слушают `127.0.0.1`.
Пароль администратора передаётся при первичной настройке в памяти и сохраняется
backend в виде хеша. Существующий пароль при повторном запуске не меняется.

Текущие тестовые сборки не имеют сертификата разработчика. Для распространения
потребуется настроить подпись Windows и подпись/notarization macOS. Механизм
обновления сохраняет проверки и ограничения ОС; системное подтверждение запуска
неподписанной программы может потребоваться и после обновления.

## Данные и резервные копии

- macOS: `~/Library/Application Support/Ovoshi Help/`.
- Windows: `%APPDATA%\Ovoshi Help\`.
- `data/`: база PostgreSQL, файлы, настройки и отметка версии.
- `logs/`: журналы компонентов.
- `backups/`: согласованные резервные копии базы и файлов.

Файлы программы заменяются при обновлении, данные лежат отдельно. В меню «Файл»
есть создание и восстановление резервной копии, а также открытие папки данных.
Перед копированием приложение останавливает backend, поиск и базу. Восстановление
сначала сохраняет текущие данные в другую копию. Пароли базы и параметры интеграций
являются частью закрытой папки данных; не публиковать её или резервные копии.

В desktop-профиле MinIO заменён локальным атомарным хранилищем, Redis — счётчиками
в единственном процессе backend. Серверный профиль сохраняет MinIO и Redis.
PostgreSQL major закреплён в сборке. Для будущего перехода между major-версиями
потребуется отдельный перенос базы; простая замена бинарников запрещена проверкой.

## Обновления

После готовности локальных компонентов приложение один раз за запуск проверяет
последний стабильный `desktop-vX.Y.Z` в
[GitHub Releases](https://github.com/ozLPanda/fresh-supply/releases).
Если версия новее установленной, предлагает «Обновить» или «Позже». При отсутствии
обновления или интернета проверка при запуске проходит без окна. В меню
«Помощь → Проверить обновления» остаётся ручная проверка с результатом.
При первом запуске проверка ждёт завершения настройки и формы переноса данных.

«Обновить» означает согласие скачать пакет и установить его с перезапуском:
сначала сохраните изменения в открытых формах. Программа показывает прогресс,
проверяет размер и SHA-256 из GitHub API, готовит пакет, создаёт согласованную
резервную копию и только затем запускает установку. Во время загрузки и подготовки
можно отменить обновление; данные ещё не меняются. Повреждённый или недокачанный
пакет не устанавливается. Ошибка подготовки или запуска помощника возвращает
текущую версию к работе. При обычном выходе отложенное обновление не устанавливается.

Windows x64 использует установленный NSIS-пакет: помощник ждёт выхода программы,
повторно проверяет SHA-256 и устанавливает EXE в тот же каталог с автоматическим
запуском. Для этого каталог должен быть доступен текущему пользователю.
На macOS загружается ZIP; проверяются пути, ссылки, ID приложения, версия и
архитектура. Помощник заменяет установленный `.app` через переименование и запускает
его средствами macOS. Требуются доступный для записи каталог установки и минимум
5 ГБ свободного места. Запуск из `.dmg` или App Translocation обновлять нельзя:
сначала переместите программу в «Программы» и запустите её оттуда.

Прежний `.app` на Mac сохраняется до успешного запуска локального runtime новой
версии. Если системный запуск не удался, помощник возвращает старую программу.
Если новая программа запустилась, но не подтвердила готовность за 10 минут, старый
пакет сохраняется для восстановления; путь записывается в `logs/mac-update.log`.
Автоматического переключения бинарников после возможных миграций в этом случае нет.
Журналы Windows: `logs/windows-update.log` и `logs/windows-update-host.log`.
Отдельный CMD launcher даёт PowerShell собственную консоль и продолжает работу
после закрытия приложения; пути и параметры передаются как данные.

Первый запуск другой версии дополнительно создаёт копию перед миграциями. Если
запуск новой версии не прошёл проверку готовности, данные возвращаются из этой
копии. После этого нужно установить предыдущий рабочий пакет из Releases.
Если восстановление прервано между заменой каталогов, приложение подхватывает
сохранённый прежний каталог, а не создаёт пустую базу.

Источник загрузки — публичный репозиторий проекта, HTTPS GitHub и его CDN.
Общий GitHub-токен в пакет не включается. Закрытый репозиторий, черновики,
предрелизы, неподходящая архитектура или отсутствие SHA-256 не разрешают установку.
В запуске из исходников доступна ссылка на выпуск; установленная программа
скачивает пакет сама. Подпись разработчика остаётся отдельным этапом.

Механизм обновления включён в выпуск 0.1.7.
Установленную 0.1.5 нужно один раз обновить готовым установщиком; её старый
механизм не умеет самостоятельно установить новые функции обновления.

## Внешние интеграции

Локальные операции работают без интернета. GPT, WhatsApp, MKS и прочие внешние
подключения требуют сети и собственных настроек. Они не копируются из `.env`
веб-проекта. Локальные параметры можно задать в `data/integrations.json`
строковыми значениями разрешённых backend env-переменных, например
`APP_GPT_ENABLED`, `OPENAI_API_KEY`, `APP_WHATSAPP_*`, `APP_MKS_*`.
После изменения нужно перезапустить приложение. Секреты не хранить в исходниках.

## Сборка из исходников

Только разработчику нужны Node 24, Java 21 JDK, Maven и интернет. Собирать на
целевой ОС/архитектуре. Первая подготовка скачивает большую модель и зависимости;
полный runtime Mac занимает примерно 2,2 ГБ до упаковки.

```bash
cd desktop
npm ci
npm run prepare:runtime
node scripts/verify-runtime.cjs
npm test
npm run test:integration
npm run dist:mac
# На Windows вместо dist:mac:
npm run dist:win
```

Готовые пакеты находятся в `desktop/dist/`. `npm start` запускает приложение
из исходников с уже подготовленным runtime. Перед первым таким запуском выполните
`npm exec install-electron`: Electron 44 скачивает бинарник для разработчика
отдельно от `npm ci` (electron-builder скачивает его самостоятельно при упаковке).
`npm run pack` создаёт каталог
приложения без установочного образа. `DESKTOP_MAVEN` позволяет указать Maven
вне PATH. Бинарные зависимости и Python-пакеты закреплены по SHA256; модель —
по ревизии и SHA256 safetensors. См. [контракт runtime](runtime-runtime-contract.md).

Для сборки Windows-установщика на Mac с уже подготовленным Mac runtime есть
дополнительные команды. Они создают отдельный `runtime-win32-x64` и результат
в `dist-win`; используются готовые Windows-бинарники и Windows wheels, а не
библиотеки Mac. Такая сборка не заменяет тест установки на Windows.

```bash
node scripts/prepare-windows-cross.cjs
node scripts/package-windows-cross.cjs
node scripts/checksums.cjs dist-win
```

Интеграционная проверка использует собственную временную базу: первичная настройка,
вход по cookie, создание категории, загрузка/скачивание файла, перезапуск,
резервное копирование, восстановление и запуск следующей версии. Также проверяются
настоящая миграция схемы и восстановление после сломанной миграции. Исходные базы
и пользовательские данные проверка не открывает.

Проверка переноса данных также ищет импортированные товары с заглавными русскими
и казахскими названиями через API каталога и подбора, формирует накладную PDF,
накладную З-2, счёт на оплату и сверку, затем повторяет проверки после перезапуска.
Повторное обновление проверяет новые, изменённые и удалённые данные сайта, замену
локальных файлов, отмену, недоступный источник, восстановление после ошибки запуска
и ручное восстановление резервной копии с локальными изменениями.
Поиск не зависит от локали существующей БД; шрифты PDF поставляются внутри backend
JAR вместе с лицензией и не требуют установки в Windows или macOS.

## GitHub-сборка

`.github/workflows/desktop-release.yml` собирает Mac arm64 и Windows x64, проверяет
runtime и интеграционные сценарии. Ручной запуск сохраняет пакеты как workflow
artifacts. Тег `desktop-v<версия desktop/package.json>` дополнительно создаёт
черновик Release с пакетами и SHA256SUMS. Публикация стабильного выпуска выполняется
после проверки установки на обеих ОС. Эта реализация не публикует код или релизы
сама по себе.

Пример для следующего выпуска после изменения версии, lock-файла и публикации
кода в `main` (версию выбирайте больше уже опубликованной):

```bash
git tag -a desktop-v0.1.9 -m "fresh-supply 0.1.9"
git push origin desktop-v0.1.9
```

В GitHub откройте Actions → Build standalone desktop installers и дождитесь
успешной сборки обеих ОС. Затем в Releases откройте созданный черновик,
проверьте установщики, добавьте описание изменений и нажмите Publish release.
Стабильный desktop-выпуск должен быть Latest без отметки pre-release: именно
его проверяет меню приложения «Помощь → Проверить обновления». Черновик
не предлагается пользователям как обновление.

Для следующего выпуска сначала измените версию и lock-файл командой
`npm version 0.1.9 --no-git-tag-version` из `desktop/`, опубликуйте изменения,
затем создайте соответствующий новый тег `desktop-v0.1.9`. Установщики находятся
в приложениях к Release; в Git хранятся исходники. Для проверки сборки без
создания Release используйте Run workflow в Actions.
