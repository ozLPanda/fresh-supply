# fresh-supply — магазин «GastroFlow» в дизайне HackAlem

Отдельный проект на основе текущей рабочей копии `firm-active-company-shop`.
Из `hackalem-ai-base` перенесён визуальный язык интерфейса. Направление магазина,
каталог, API, бизнес-правила, права доступа и остальные модули сохранены.
Исходные проекты не требуется изменять или запускать для работы нового стека.

Настольная версия с локальными backend и базой описана в
[desktop/README.md](desktop/README.md). План и состояние реализации:
[docs/desktop-app-plan.md](docs/desktop-app-plan.md).

## Быстрый запуск интерфейса

Нужен Node.js 24+ (библиотека сканера штрихкодов требует Node 24). Из корня проекта:

```bash
cd frontend
npm ci
npm run dev
```

Интерфейс: `http://localhost:5175`. Запросы `/api` и `/uploads` идут через Vite
к отдельному backend `http://127.0.0.1:8084`. Для данных и входа нужен запущенный
backend; одна команда Vite не поднимает базу данных и API.

Для просмотра с уже запущенным исходным API можно явно указать
`DEV_API_TARGET=http://127.0.0.1:8083 npm run dev`. Это **общие данные исходного
магазина**, а не независимая база: используйте такой режим только для просмотра,
не оформляйте заказы и не изменяйте данные. Настройка не сохраняется в исходниках.

## Отдельный полный стек

Docker Compose запускает PostgreSQL/pgvector, Redis, MinIO, embeddings, Java 21
backend, Vite frontend и Caddy. Первый запуск на пустой базе создаёт проект
без товаров, категорий, изображений товаров и ценовых групп, с одним аккаунтом
администратора. Роли, права, системные настройки, нулевой кошелёк администратора
и основной склад сохраняются: они нужны для работы модулей.
Текущая база исходного магазина и его загруженные файлы не копируются.

Для новой базы Flyway начинает с `B015__empty_project.sql`, затем применяет
`V016` и последующие миграции. Начальное заполнение каталога из `V012` и `V015`
при этом не выполняется. Уже установленные базы продолжают использовать свою
историю миграций; их товары, категории и аккаунты не удаляются. Обычный
`git pull` и перезапуск backend не очищают существующую базу.

```bash
cp .env.example .env
# При желании включите APP_ROTATE_SEED_ADMIN и задайте свой пароль (16+ символов).
docker compose config --quiet
docker compose up -d
```

При первом запуске без локальных образов соберите их однократно командой
`docker compose build backend frontend embedding-service`, затем повторите
`docker compose up -d --no-build`.
Embeddings загружает модель при сборке, поэтому первая сборка требует сети и времени.
Локальное S3-хранилище использует готовый образ
`pgsty/silo:RELEASE.2026-09-16T00-00-00Z` — поддерживаемый форк MinIO от PGSTY.
Прежний образ `minio/minio` больше недоступен для публичного скачивания.
Имя сервиса `minio`, переменные `MINIO_*` и адрес backend сохранены.
При первом запуске на Windows/WSL сборка хранилища не нужна: выполните
`docker compose pull minio`, затем `docker compose up -d --no-build`.
Проверены запуск amd64, healthcheck и создание/чтение/удаление объектов в пустом
тестовом хранилище. Перед переходом с уже заполненного MinIO сделайте резервную
копию и проверьте [инструкцию миграции PGSTY](https://silo.pgsty.com/compatibility/migration/);
совместимость существующей базы IAM и настроек в этой проверке не тестировалась.
В дальнейшем исходники frontend/backend подключены через bind mounts: изменение
стилей не требует пересборки контейнеров. Подробности в `AGENTS.md`.

| Сервис | Локальный адрес |
| --- | --- |
| Магазин | http://localhost:5175 |
| Админ-панель | http://localhost:5175/admin/login |
| API | http://localhost:8084 |
| PostgreSQL | 127.0.0.1:5434 |
| Embeddings | 127.0.0.1:8002 |
| Gateway HTTP | http://localhost:8085 |
| Gateway HTTPS | https://localhost:8445 (локальный сертификат Caddy) |

Все публикации привязаны к loopback. Compose-проект — `ovoshi-help`, volumes
получают его префикс. Cookie сессии — `ovoshi_help_session`, отдельная от исходного
магазина. Служебная cookie Spring — `ovoshi_help_servlet_session`.
Никакие контейнеры исходного проекта не останавливаются.

Начальные учётные данные задаются сохранёнными миграциями, не аккаунтом из
Keychain исходного магазина. Вход выполняется **по телефону**. Телефон начального
администратора можно посмотреть в своей новой БД:

```bash
docker compose exec postgres psql -U company_shop -d company_shop -c "select phone from users where email = 'admin@active.kz';"
```

В локальном режиме без ротации исходный seed-пароль — `password`. Если в `.env`
включена `APP_ROTATE_SEED_ADMIN=true`, используется заданный вами
`APP_BOOTSTRAP_ADMIN_PASSWORD` (не меньше 16 символов). Секреты не храните в Git.

Ключи GPT, WhatsApp, MKS и Web Push оставлены пустыми; модули сохранены, но их
внешние подключения нужно настроить для нового магазина отдельно.

## Состав и проверки

Каталог и товары, корзина и оформление, профиль и заказы, CRM, поставщики и MKS,
WhatsApp, склад и документы, закупки, прайс-импорт, аналитика, роли, аудит,
уведомления, PWA и 3D-просмотр остаются в проекте. Полная карта маршрутов и
границы переноса — в `docs/project-merge.md`.

```bash
cd frontend
npm run build
```

Backend использует Java 21 и Maven: `mvn -f backend/pom.xml test`. Интеграционные
тесты могут требовать PostgreSQL; не запускайте их против исходной рабочей базы.
Админ-страницы проверяйте после входа через `/admin/login`.

Продакшен не развёрнут. Инструкции и ограничения шаблонов: `PRODUCTION.md`.

Настольное приложение называется `fresh-supply`. При обновлении сохраняются прежние
`appId` и папка данных `Ovoshi Help`: менять их нельзя без отдельной миграции.
Установщики с прежним префиксом `OvoshiHelp-` в релизах — копии для проверки обновлений
из версии 0.1.2; новые установщики называются `fresh-supply-…`.
